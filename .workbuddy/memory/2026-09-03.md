### 关键结论
- 唯一需要日常改的配置文件：`src/config.ts`（siteConfig / navBarConfig / profileConfig / licenseConfig / expressiveCodeConfig）
- 文章：`src/content/posts/`，两种形式——`xxx.md`（slug = xxx）或 `xxx/index.md`（slug = xxx，封面图与 md 同目录，frontmatter 用 `./cover.jpeg`）
- 文章 schema 定义在 `src/content/config.ts`（title/published/updated/draft/description/image/tags/category/lang）
- 侧栏小组件顺序：`src/components/widget/SideBar.astro`；Profile / Categories / Tags 分别对应 `widget/Profile.astro`、`widget/Categories.astro`、`widget/Tags.astro`
- 导航栏：`src/components/Navbar.astro`；预设项在 `src/constants/link-presets.ts`，字体/文案走 i18n
- About 页面内容：`src/content/spec/about.md`（不是组件）
- 视觉配置三层：`src/config.ts` 的 `themeColor.hue`（单一色相，驱动整套 oklch 配色）→ `src/styles/variables.styl`（CSS 变量，明暗双套）→ `src/styles/main.css` / `markdown.css` / `scrollbar.css` / `transition.css`（组件类）
- 字体：`src/layouts/Layout.astro` 顶部 import @fontsource/roboto，代码字体在 `astro.config.mjs` 的 expressiveCode styleOverrides
- 页面宽度 / 每页条数 / Banner 高度：`src/constants/constants.ts`（PAGE_SIZE=8, PAGE_WIDTH=75rem, BANNER_HEIGHT=35vh）

### 环境与坑
- **当前沙箱环境无法完整跑通 `pnpm build`**：Astro 构建末期要删除 SSR 临时产物 `dist/chunks/`（约 50 个文件），被环境的批量删除保护拦截，导致 `astro build` 退出码 1，后续 `pagefind --site dist` 未执行。**页面 HTML/CSS 产物本身已全部正常生成**（index/about/archive/5 篇文章均已输出）。这是环境限制，不是项目问题。
- `pnpm dev` 同样因 Vite 清理 `node_modules/.vite` 缓存被拦截而无法启动（502 / exit 1）。
- 结论：在本沙箱内只能用 `pnpm build` 验证产物，且需人工忽略末尾删除报错；要跑 dev server 需用户在本机终端执行。

### 重要发现：样式的加载机制（已用实验验证）
- **源码里没有任何地方 import `src/styles/` 下的样式文件**，`src/components/GlobalStyles.astro` 是空文件且从未被引用。已与上游 saicaca/fuwari 主线逐文件核对（package.json / main.css / markdown.css / GlobalStyles.astro / Layout.astro），**完全一致**——所以空文件是原版设计，不是本地损坏。
- 但实验证明：**Vite 会把 `src/styles/` 下每个 .css/.styl 当作独立入口单独编译**（放一个含错误语法的探针文件进去，即使无人 import 也会报错）。因此每个文件拥有独立 Tailwind 上下文。
- 由此产生一个脆弱点：`markdown.css` 第 23 行有 `@apply ... link ...`，而 `link` 类定义在 `main.css` 的 `@layer components` 里。跨文件 `@apply` 在 Tailwind 3 中默认不可见，依赖编译顺序/上下文共享。
- **实测踩坑**：中途尝试跑 dev server 后，Vite 依赖缓存失效，构建开始报 `The 'link' class does not exist`（markdown.css:23）。用全新 cacheDir 冷构建也复现。但**再跑两次后自行恢复正常**。判断是沙箱阻断删除导致 Vite dep 预打包处于中间态引发的偶发问题，非项目缺陷。若以后再遇到，优先让用户在本机终端执行 `rm -rf node_modules/.vite && pnpm build`。
- 结论：改 `src/styles/*` 是有效的（已确认 `.card-base`、`.custom-md`、`--radius-large` 都在产物 CSS 中），但**每次改完必须完整构建验证一次**，不要只跑 dev。

### 阶段 3 视觉层改动（已完成并验证）：中文字体栈
- **问题**：`tailwind.config.cjs` 原为 `sans: ["Roboto", "sans-serif", ...defaultTheme.fontFamily.sans]`。通用 `sans-serif` 排在 `system-ui` 之前，浏览器会提前回退到默认无衬线字体，永远轮不到 PingFang SC / 微软雅黑，中文渲染非最优。这是上游 Fuwari 的既有写法，不是本地问题。
- **改法**：把中文字体插到 Roboto 之后、generic 之前：
  `["Roboto", "PingFang SC", "Hiragino Sans GB", "Microsoft YaHei", "Source Han Sans SC", "Noto Sans CJK SC", ...defaultTheme.fontFamily.sans]`
- **关键原则**：中文字体必须排在 generic `sans-serif` 之前；generic 放最后。浏览器按字形逐级回退，西文命中 Roboto、中文命中 PingFang/YaHei。
- 验证：产物 CSS `_page_.BBWAsNPo.css` 含完整字体栈，`index.html` 确实引用该新 hash。
- **dist 残留辨识方法**：沙箱不能清 dist，新旧 CSS 会并存。判断哪个生效要看 `index.html` 引用的 hash + 文件 mtime，不要只看文件是否存在。
